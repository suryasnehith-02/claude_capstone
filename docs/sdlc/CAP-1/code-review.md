## 7. Round 3 dialog analysis (static, line by line)

Reading of `dialog.js` (95 lines). State is one variable `current` (`{id, promise, resolve, returnFocus}` or null). `finish(confirmed)` (`:28-38`) does nothing when `current` is null; otherwise it copies `current`, sets it to null FIRST, focuses `returnFocus` if it has a `focus` function, then resolves. `onClosed()` (`:42-47`) returns when `dialogEl.open` is true, else calls `finish(returnValue === 'confirm')`. `closeWith(v)` (`:49-52`) calls `dialogEl.close(v)` then `onClosed()`. Wiring (`:54-57`): Cancel and Delete click handlers, a `close` listener and one `MutationObserver` on the `open` attribute, all pointing at `closeWith` or `onClosed`. No syntax error, no undefined identifier, no stale import, no stale `nextClose`; the observer callback and the event listener receive extra arguments that `onClosed` ignores. `export` surface is unchanged: `createConfirmDialog` returns `{ confirmDelete, isOpen }`, and `app.js:30, 52` uses only `confirmDelete`.

**(1) Exactly once on every path.** Because `finish` is guarded by `current` and nulls it before resolving, a second call can never resolve the same promise again. Each path:
- Cancel button: `close('cancel')` removes `open` and sets `returnValue = 'cancel'`; `onClosed` sees `open === false` and calls `finish(false)`. The queued observer microtask and the later `close` event find `current === null` and do nothing. Resolved once, false.
- Delete button: same with `'confirm'` -> true.
- Escape: the browser fires `cancel` (not prevented, nothing listens), closes the dialog leaving `returnValue` at `''` (reset at `:77`); the observer microtask runs `onClosed` -> `finish(false)`. The `close` event later is a no-op. Resolved once, false.
- Backdrop or programmatic `close()`: same as Escape. (The CSS has no backdrop-click handler, so a backdrop click does nothing unless the platform closes the dialog; then same path.)
- A native `close` event arriving late: `onClosed` -> if the dialog is open again (a newer opening) it returns without touching `current`; if no newer opening exists, `current` is null and `finish` does nothing; if a newer opening was already closed again, the old event finishes that newer confirmation with the current `returnValue`, which is the newer closing's own value, so the result is still right. So the OLD close event can never resolve the NEW confirmation with the OLD value: `returnValue` is reset at each opening (`:77`) and re-written only by the newer close.
- Re-entry, same task, dialog open: returns the same pending promise (`:75`), `showModal` not called again (`dialog.test.js:125-133, 151-160`).
- Re-entry, different task, dialog open: resolves `false` immediately and leaves the open dialog and `current` unchanged (`:75`; test `dialog.test.js:162-175`).
- Re-entry after a close that has not been noticed yet (the observer microtask has not run): `:71-73` calls `onClosed` first, which finishes the old confirmation, then a new one opens. `finish` runs before `showModal`, so the old promise gets the old `returnValue`; the observer record produced later is processed with `open === true` and ignored (test `dialog.test.js:135-149`). Correct.
- `showModal` throwing: `current` is set to null and `Promise.resolve(false)` returned (`:84-89`); nothing is left pending. (`textContent` and `returnValue` were already changed; harmless.)
- Double activation of Delete (second `.click()` after the first): `close` on an already closed dialog is a no-op in the platform, `onClosed` -> `finish` no-op. No second resolve.
I found no path that leaves the promise pending while the dialog is closed, because every closing either goes through `closeWith` (which finishes at once) or removes the `open` attribute (observer) or fires `close` (listener). The one path that stays pending is removal of the whole dialog element from the document while it is open (no attribute change, no `close` event guaranteed); the app never does this, and `afterEach` closes the dialog before `sandbox.remove()`.

**(2) The MutationObserver.** It is created once per `createConfirmDialog` call (`:57`), not per opening, so repeated openings add no observers; `app.js:52` creates the dialog once per app. It is never disconnected and no handle is kept (CR-15 nit); it is bounded and goes away with the element. `attributeFilter: ['open']` limits callbacks to `open` changes. When `showModal` sets `open`, the callback runs `onClosed` with `open === true` and returns; so a mere re-opening cannot resolve anything. Records are batched and `onClosed` ignores them, so a close followed by a re-open in the same turn gives one callback seeing `open === true`; the old confirmation has already been finished by `:71-73` in that case, so nothing is lost. I found no bad interaction with the `open` attribute set by `showModal`.

**(3) Focus and requests.** Focus returns to `returnFocus` inside `finish`, on every resolving path (Cancel, Delete, Escape, programmatic close, observer or event). It happens after the platform's own focus restoration in `close()`, because `finish` is called after `close()` returns (buttons) or in a later microtask (Escape), so the caller's element wins; if `returnFocus` is null it is skipped (`dialog.test.js:207-214`). When `showModal` throws, focus is not touched by the dialog (the app then calls `ui.focusControl` itself, `app.js:438-440`). In `app.js:421-473`: `confirming` and `state.pending` are checked synchronously before the first `await` (`:422-423`), `askConfirm` is called synchronously, so a second Delete click while a confirmation is open returns at once. After the confirmed answer, `state.pending.set(id, 'delete')` (`:446`) happens before `api.deleteTask(id)` (`:449`) in the same synchronous run, and the guard at `:443` blocks a second send; so exactly one `DELETE` per confirmed dialog (AC-9, AC-13), with the same result for the real-dialog test at `app-edit-delete.test.js:507-521`. A declined or rejected confirmation never reaches `:446`.

**(4) Could the 7 failing tests now pass in current Chromium?** Evidence from the human's failure lines: in the Cancel and "Cancel sends no request" cases the dialog was already closed and no request had been sent, but the promise had not produced its result and focus had not returned to the Delete button. A programmatic `.click()` does not focus the button, so the platform's own focus restore cannot have placed focus there; only `finish` can. That fits "the handler that ran `finish` (the native `close` listener) had not run when the test looked", i.e. late or missing `close` events. The new code does not depend on that event for the buttons (resolution inside the click) and depends only on a microtask for Escape and `close()`, which are queued when the attribute is removed and run before `await settle()` (a macrotask) or `await pending` returns. Each of the 7 tests now waits only on the `confirmDelete` promise or one `settle()`, so I think they should now pass. I am not sure of: (i) the actual cause, which the developer rates LOW confidence and which I could not prove (see the note on failure 5 in section 6); (ii) whether Chromium 150's dialog `close()` removes the `open` attribute synchronously in every case, including with the new `closedby` and `requestClose()` behaviour (I believe so); (iii) behaviour of this embedded browser when its page is not focused or visible; (iv) that no other thing in that environment (for example a focus-related restriction) makes `document.activeElement` differ.

**(5) New defects.** No syntax, import, export or id defect found. Test determinism by reading: no test uses a timer to wait for a native event; no fake timer interplay in the dialog tests; the `afterEach` hooks close any open dialog (which resolves any still-pending promise through the observer, with `returnFocus` possibly pointing at a node about to be removed, harmless). `dialog.test.js:143` is deterministic (`dispatchEvent` is synchronous; the guard is the `open` check). The `track` helper registers its `then` before the test awaits, so `seen` is filled before the test continues (microtask order).
