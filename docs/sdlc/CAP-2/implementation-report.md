### What was built
- **`ApiGatewayFilter`** (`final`, extends `OncePerRequestFilter`, constructor `(RouteTable, BodyGate, ApiResponses)`; deliberately NOT a Spring bean, so Boot does not register it a second time; `WebConfig` builds it). REQUEST dispatch: request id (UUID) into the MDC key `requestId` and the attribute `ApiGatewayFilter.REQUEST_ID_ATTRIBUTE`; `X-Content-Type-Options: nosniff`; P1 `RouteTable.resolve(method, getRequestURI())`; on a match the `RouteMatch` goes into `ApiGatewayFilter.ROUTE_ATTRIBUTE`; P2/P3 `BodyGate.check`; the `RawBody` goes into `ApiGatewayFilter.RAW_BODY_ATTRIBUTE` (T-13's resolver reads these two attributes; they are the class names of `RouteMatch` and `RawBody`). A rejection is written with `setStatus`, `Allow` (405 only), `Content-Type: application/json`, `Content-Length`, the fixed bytes from `ApiResponses.fixedError` (none for HEAD) and `flushBuffer()`; `sendError` is never called (a test response class fails the test on any `sendError`, and `SourceRulesTest` scans the source). Boundary-only mode on ERROR dispatch (and `doFilterNestedErrorDispatch`, `shouldNotFilterErrorDispatch()` false): no P1-P3; request id restored from the attribute (created if absent); nosniff; if no route was recorded and the original URI (`jakarta.servlet.error.request_uri`) plus the method do not match a route (TRACE), it writes the fixed body for the dispatched status (`ErrorCode.forContainerStatus`) and does not call the chain; an unmapped status in that short-circuit is logged once at ERROR (nobody else would). Everything runs inside `try/catch (Throwable)`: a client abort (an `IOException` whose class simple name is `ClientAbortException` or `AsyncRequestNotUsableException`, or an `EOFException`, anywhere in the cause chain) is DEBUG only; anything else is logged once at ERROR (`requestId`, `method` if it is letters only, `route` template or `(none)`, the throwable; never the URI, query, body or raw id) and, if the response is not committed, `reset()` and the 500 envelope are written. The MDC is put back to its previous value in `finally`.
- **`TomcatConfig`**: a `WebServerFactoryCustomizer<TomcatServletWebServerFactory>` adds a `TomcatConnectorCustomizer` (`setAllowTrace(true)`, `setEncodedSolidusHandling("passthrough")`, `setEncodedReverseSolidusHandling("passthrough")`; the method exists in 11.0.27) and a `TomcatContextCustomizer` that puts a quiet `ErrorReportValve` (`setShowReport(false)`, `setShowServerInfo(false)`) into the host pipeline (or quiets one already there).
- **`WebConfig`**: `FilterRegistrationBean<ApiGatewayFilter>` named `apiGatewayFilter`, `Ordered.HIGHEST_PRECEDENCE`, REQUEST and ERROR, `/*`; `configureContentNegotiation`: `ignoreAcceptHeader(true).defaultContentType(MediaType.APPLICATION_JSON)`.
- Character-encoding filter: disabled by `spring.servlet.encoding.enabled=false` (already in `application.properties`); it is absent (see V-9).

### Deviation and surprise (needs the reviewer's eye)
1. **The finding's rule alone broke the real abort case, so a second signal was added.** After the CR-1 change the full suite failed once (run 81): `GatewayFailureContractTest.aClientThatDisappearsMidBodyIsNotAFailure` (CP-B, a real socket closed mid-body). The gateway sees `ClientAbortException` while reading the body and logs DEBUG, but Tomcat then runs the ERROR dispatch for the same request with a **bare `java.io.EOFException`** as `ERROR_EXCEPTION` (log line: `FallbackErrorController ... exceptionClass=java.io.EOFException`), and `FallbackErrorController` had used the old "any EOF" rule to stay quiet. Following the finding literally would have logged that real abort at ERROR; keeping the old rule is exactly the CR-1 bug. Resolution: the gateway records on the request that it saw the client leave (`CLIENT_ABORT_ATTRIBUTE`, only in the two places where it already logs "client went away"/"body could not be read"), and the error controller treats the dispatch as an abort only when that attribute is set or the exception itself is one of the two abort types. A bare `EOFException` with no gateway record is now an ERROR entry (unit test above). Why Tomcat reports an `EOFException` there is my reading of one log, not a separate Tomcat observation. No HTTP behaviour or public interface changed; the attribute is internal to the request.
2. `ApiExceptionHandler.unexpected` for a real abort now returns the 500 envelope (as the finding says) instead of `null`; on a gone client the write fails and the gateway tolerates that (`fail` catches the secondary failure). Observed only through unit tests; the real-socket path goes through the gateway and the error controller, not the advice.
3. The test `theClientAbortTestIsAnnouncedByTheClassNameOnly` and the private look-alike `ClientAbortException` class in `ApiGatewayFilterTest` were removed: the filter now matches the real types, and the tests use Tomcat's real class (already on the test class path, used by two other tests). The `EOFException("eof")` row of `aClientAbortFromTheChainIsNotAFailure...` was replaced (it asserted the CR-1 behaviour being removed).
